[CRITICAL] F-1 — the review authority is re-resolved LAZILY after the negative control when gh
           was absent at startup: the C5 class survives on that state, on a SOUND lane, silently.
  runtime/scripts/verify.py:618-619
    > if _Authority.gh is None and _Authority.custody is None:
    >     _Authority.resolve()  # a library caller that never ran main(): pin on first use (F-1)
  runtime/scripts/verify.py:677 (inside resolve()):
    > cls.reset()
  Motivating spec line (build-fix.md F-1a): "resolve the review authority to an ABSOLUTE path
  ONCE, at startup, BEFORE any negative-control execution, and invoke only that resolved path —
  a mid-run PATH write can never redirect the review leg".
  Why: main() DOES pin at startup (verify.py:2407), but when `shutil.which("gh")` finds nothing
  the pinned state is (gh=None, custody=None) — indistinguishable from "never resolved". verify()
  runs check_negative_control (line 2275, executes worker code) BEFORE check_review (line 2280);
  fetch_reviews then sees the sentinel and calls resolve() AGAIN, mid-run, which (a) picks up a
  gh the control just planted first on PATH, (b) runs it, and (c) reset() wipes `lane` and
  `repo_source`, so the sound-lane fail-closed can never fire. review_leg() was already evaluated
  (custody None → []) before the fetch, and check_review returns that pre-fetch `authority` — [].
  Reproduced (scratch copy, scratchpad/repro/c5_absent_gh.py, step 5): PATH = <writable dir>:
  /usr/bin:/bin with no gh; _Authority.resolve(provenance="ci", explicit_repo="o/r") →
  gh=None custody=None lane=provenance=ci repo_source=explicit; stub gh planted; ONE
  check_review(...) call →
    REAL FLOW(5) check_review -> [] | fatal? False
    state after(5): gh=/var/folders/.../worker-drop-.../gh custody=worker-writable lane=None repo_source=None
  i.e. a stub-fabricated APPROVED is accepted with NO fatal and NO advisory NOTE on provenance=ci.
  This is exactly "a stub gh in a writable PATH dir ... a same-run GREEN" the spec forbids, on the
  realistic state where the coordinator host (CI container, sandbox) has no gh installed.
  The killer test (tests/test_verify.py:3996-3999) always installs a stand-in "real" gh before the
  run, so this state is untested.
  Fix shape: make "resolved" a distinct state (e.g. `resolved = False` flag, or a sentinel object
  for "absent"), never re-resolve once main() pinned; fetch_reviews on absent → "gh not on PATH"
  fail-closed as before. On a sound lane, absent-at-startup should arguably be fatal in
  review_leg() itself (E1d). Add the absent-at-startup variant to
  ReviewAuthorityPinnedBeforeTheControl (drop `realgh` from PATH; assert rc 2 and that
  dropped_log never appears).

   `choices=("ci","mcp","sdk","dispatch")` so a typo is a usage error (exit 1), and a corrected
   thread reply that does not claim a verdict NOTE.

T2 #4060043696 "Writable binaries classified trusted" (verify.py:701) — HOLD (spec-authorized),
   but the reply's stated premise is off-target and should be corrected in-thread.
   Code: the SYSTEM_BINS test is on the PATH-entry dir (verify.py:700) and includes
   /opt/homebrew/bin. On THIS build host: `/opt/homebrew/bin` is `drwxrwxr-x ravindra` and
   `which gh` → /opt/homebrew/bin/gh — i.e. the host's actual gh lives in a user-writable dir
   that classify() calls "system". The reply's evidence ("Premise false on the build host
   (/usr/local/bin is drwxr-xr-x root)") cites the directory gh is NOT in. Greptile's premise is
   TRUE on this host. The conclusion still holds by spec authority — build-fix.md F-1(b) carves
   out "a standard system bin dir" and the classify docstring names Homebrew's prefix as that
   convention — and a same-uid worker that can write /opt/homebrew/bin can equally write the
   coordinator's checkout, which F-5's toolchain binding exists to catch. Adjudication: HOLD;
   correct the reply's evidence; add one sentence to docs/verify-gate.md naming the Homebrew
   carve-out as an accepted residual on same-uid hosts.
