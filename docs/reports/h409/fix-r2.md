## G-1 (CRITICAL) — gh absent at startup was "unresolved", and the review leg re-resolved AFTER the executed control

### Reproduction on HEAD-before-fix (78df68a6)

`scratchpad/repro_g1.py` subclasses the unit's own C5 fixture (`ReviewAuthorityPinnedBeforeTheControl`)
and drops the stand-in `realgh` from PATH, so no gh exists when `main()` pins:

```
NATIVE rc= 0
planted: True consulted: True
SOUND rc= 0
planted: True consulted: True
FAILED (failures=2)
```

Exit 0 on BOTH lanes (`--provenance ci` included), with the stub the control planted answering
the review leg — the C5 same-run false GREEN, exactly as review-spec.txt / review-tests.txt M1 /
review-standards.txt S-1 described.

### Root cause (the class, not the symptom)

`_Authority.resolve()` left `(gh=None, custody=None)` when `shutil.which("gh")` found nothing —
byte-identical to the never-resolved state — so `fetch_reviews`' library-caller fallback
(`if gh is None and custody is None: resolve()`) fired mid-run, AFTER `check_negative_control`
had executed worker code, found the gh the control planted, and `reset()` wiped `lane` and
`repo_source` so the sound-lane refusal could never fire.

### Fix (`runtime/scripts/verify.py`)

- `custody` gains a third RESOLVED value, `"absent"`: `resolve()` sets it when no gh is found.
  `None` now means UNRESOLVED and nothing else.
- One guard, `_Authority.ensure()`, replaces the inline fallback: it resolves only when
  `custody is None`. A pinned run — absent included — is never re-resolved. Called from
  `fetch_reviews` (direct library callers) and, new, at the top of `verify()` — so a library
  caller that runs the control through `verify()` is pinned BEFORE the control, not after it.
  `main()` pins at startup as before; resolution therefore happens exactly once per run on
  every entry path.
- `review_leg()` treats `"absent"` as a state of its own:
  - sound lane → fatal `review_authority: gh absent at startup (… pinned once, before the
    control, and never re-resolved — h409 F-1) — a lane claiming soundness (provenance=ci) has no
    independent review authority to consult; fail-closed`
  - advisory lane → `NOTE: review_authority: advisory (gh absent at startup …)`, and
    `fetch_reviews` then refuses with the same reason. `check_review` now returns the advisory
    NOTEs beside a fetch refusal instead of dropping them, so the state is recorded on the verdict.
- No lane passes with gh absent (it never did — "gh not on PATH" was already a fetch refusal);
  the change is that the refusal can no longer be dodged by planting a gh mid-run.

### Killer fixture now covers BOTH startup states (`tests/test_verify.py`, `ReviewAuthorityPinnedBeforeTheControl`)

The fixture builds a second environment, `_env_no_gh`: PATH = the empty droppable dir + a
`tools` dir holding only a symlink to git (so the fixture is host-independent — a CI runner with
`/usr/bin/gh` cannot leak one in). Three new tests, all asserting the control EXECUTED, the stub
WAS planted, and `dropped_log` never appeared:

- `test_with_no_gh_at_startup_the_native_lane_refuses_and_records_the_absence` — rc 2, the
  NOTE on stdout, `cannot fetch reviews` on stderr.
- `test_with_no_gh_at_startup_a_sound_lane_fails_closed_naming_the_lane` — rc 2,
  `review_authority` + `provenance=ci` on stderr, no advisory NOTE.
- `test_an_absent_pin_is_terminal_for_a_library_caller_too` — pin absent, then put a gh on
  PATH, then `fetch_reviews`: still `(None, "absent")`, refusal names `gh absent at startup`.

The original present-at-startup tests are unchanged and still pass.

## G-3 (tests R6–R7 / standards S-3) — the F-5 file set was two unbound literals

### Reproduction on HEAD-before-fix

review-tests.txt R6/R7: dropping `dispatch-sign.py` from EITHER `run_report.TOOLCHAIN_FILES` or
`verify._Transcript.TOOLCHAIN` left the suite green (`Ran 554 … OK` / `Ran 631 … OK`), because
`test_run_report`'s fixture derives its expected set from the production constant.

### Fix (`tests/test_run_report.py`, `TranscriptBindsTheVerifierToolchain`)

One cross-tool parity test, `test_the_file_set_is_one_set_on_both_sides_and_is_what_the_verifier_loads`:

1. `run_report.TOOLCHAIN_FILES == ("verify.py", "_verify_sig.py", "diff_scope.py", "ed25519.py", "dispatch-sign.py")`
2. `verify._Transcript.TOOLCHAIN ==` the same literal (verify.py loaded by path, as test_verify does)
3. the literal `==` the set of siblings the scripts actually load by path — a transitive walk from
   `verify.py` over every `Path(__file__).resolve().parent / "<x>.py"` / `_HERE / "<x>.py"` load
   (which is how `dispatch-sign.py` reaches `ed25519.py`).

(1)+(2) RED when a sibling is dropped from either side; (3) REDs when a new by-path sibling is
added to verify.py and left off either list — the "silent on the unsafe side" case S-3 named. The
consumer keeps its own literal on purpose: reading the set from verify.py at grade time would let
a substituted verify.py shrink what run_report checks.
