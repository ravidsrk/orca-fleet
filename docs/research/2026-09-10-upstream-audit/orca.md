## 5. New mission candidates (Orca-substrate-grounded)

Each is tested against the five-point identity test (ARCHITECTURE.md:26-41) versus the 17 missions.

### A. **screen-prove-it** — *the desktop app's user-visible behaviour is proven through the OS, not the DOM*
- **Outcome:** every flow in the run's set is driven through the real app window (native/Electron/webview) via the accessibility tree, with each action's effect `verified` by read-back, and each fix re-proven the same way.
- **Unit of work:** one desktop-observed defect (or one QA pass over one flow) with an `orca computer` action log.
- **State machine:** GRANT (permissions: `orca computer permissions --id accessibility/screenshots`; `capabilities --json`) → BASELINE (per flow: `get-app-state` snapshots + screenshots at BASE head) → REPRODUCE (action log where the failing step is `unverified`/wrong read-back) → FIX (rw worker) → REVIEW → LAND → RE-VERIFY (same action log at head SHA; every action `verified`) → NEGATIVE CONTROL (revert on a throwaway branch → the same step fails again) → PROVEN / PROVEN-WITH-PARKED.
- **Convergence proof:** for every defect: repro log with the failing verification tier + fix PR + re-drive log where each mutating action is `verified` (not `unverified (synthetic input)`), bound to `head_sha`; revert-RED receipt; `screenshot.path` artifacts in the manifest. The verification-tier vocabulary is the runtime's, so a worker cannot narrate "clicked it".
- **Ordering/isolation:** one window-owning lane per app instance (focus is a shared resource; `window_not_focused`/`--restore-window` races); builders parallel in worktrees, the desktop lane serial.
- **Parking:** `app_blocked`, `unsupported_capability`, missing OS permission (human grant), an action that only ever returns `unverified (synthetic input)` → PARKED with the exact step.
- **Terminal states:** PROVEN, PROVEN-WITH-PARKED.
- **Not one of the 17:** field-test-it's unit is a *device*-observed defect with the emulator/adb oracle (`field-test-it/SKILL.md:8,51-60`) — different oracle, different pairing state machine, no `verified`/`unverified` action tiers; access-it's oracle is WCAG on a rendered surface, not app behaviour; review-it is read-only. Shares only "reproduce → fix → re-verify", which the identity test explicitly discounts.
- **Rides:** `computer-use` (all verbs), `orchestration`, `orca-cli` (`terminal read --screen` for TUI apps).
- **Honest reasons to reject:** macOS-first provider (Linux/Windows screenshots "may come from the visible desktop region" and use a local operation file, guide:73,116); a desktop lane cannot run in an ephemeral VM, so it lives on the mortal host with a `rw` worker driving arbitrary apps — the sandbox policy's weakest posture; demand is unproven for orca-fleet's users (web/CLI repos).

### B. **sandbox-it** — *destructive and exploit work runs only on disposable machines, provably created and destroyed*
- **Outcome:** every `danger`-profile unit in a run executed on a per-workspace environment that was doctored green, paired, used, harvested, and destroyed — with receipts for each transition.
- **Unit of work:** one sandbox lane (recipe id × instance) bound to one task.
- **State machine:** DOCTOR (`vm recipe doctor <id> --repo-path … --json` with zero `fail` and zero `warn`) → PROVISION-PROOF (`--provision` once per run, `provisionTranscript` archived) → CREATE (recipe `create` → `pairingCode`/SSH block; `environment add --pairing-code`) → PLACE (`worker-start --task … --on <env> --worktree new-top-level --repo <exact remote selector>`) → RUN (`worker-list --run --include-remote`; liveness `live`, never act on `unverifiable`) → HARVEST (`git push` to the lane's work branch from inside; `worker-read --dispatch` transcript as evidence) → DESTROY (recipe `destroy`; verify the provider resource is gone) → CLOSED / CLOSED-WITH-LEAK.
- **Convergence proof:** per lane: doctor receipt · create JSON · dispatch id · pushed `branch@sha` reachable from the mortal host · destroy receipt + provider re-list showing absence · no snapshot taken after `orca serve` ran (identity leak rule). Negative control: a lane whose `destroy` is stubbed must be reported LEAKED by the verifier.
- **Ordering/isolation:** N lanes ↔ N environments; the Run stays on the coordinator host; every follow-up by Dispatch ID.
- **Parking:** paid steps (`--provision`, snapshots) and interactive agent login are human checkpoints (guide:18-27); `capability_unsupported` / `host_unavailable` → PARKED, never "exited".
- **Terminal states:** CLOSED, CLOSED-WITH-LEAK (a leak is a degraded terminal that stops any chain).
- **Not one of the 17:** harden-it's unit is a finding under a threat model; its danger lane is *consumed* here. pin-it re-witnesses doctrine, not lanes. clean-sweep's denominator is findings. This mission's denominator is lanes and its oracle is provider state + pairing — none of the 17 has it.
- **Rides:** `orca-per-workspace-env` (+ `provider-vercel`/`ssh-host`/`failure-modes` refs), `orchestration` (`--on`, `--include-remote`), `orca-cli`.
- **Honest reasons to reject:** it is arguably a *runtime policy* (`sandbox-policy.md`) plus a script, not a user-facing outcome ("destroy what you created" is hygiene); the paid-step checkpoints make it hard to run unattended; one provider reference (Vercel) is worked upstream — others are the user's homework. Strongest counter-argument: the 17 already promise the lane exists and nothing implements it — a mission is how orca-fleet gets a `proof:` tier on that promise.

### C. **triage-it** — *every open tracker ticket has a verified state, an owner, and a next action*
- **Outcome:** the open Linear set is enumerated, each ticket is classified against the codebase (real / duplicate / refuted / needs-human), moved to the right workflow state with a single completion comment, and duplicates are parented — with `linear_write_unconfirmed` replays so no write is double-applied.
- **Unit of work:** one ticket.
- **State machine:** ENUMERATE (`linear list --filter open --team <key> --workspace <id> --json`, page `--cursor` until `truncated:false`; T0 recorded) → READ (`issue <id> --full --json`, `inlineMedia` fetched before the signed URLs expire) → CLASSIFY (skeptic triage in an `ro` worker) → ACT (`status set`, `label add`, `create --parent-current` for follow-ups, `comment add --body-file -`; every write single-attempt, replayed once by `writeId` on `linear_write_unconfirmed`) → RE-ENUMERATE → TRIAGED / TRIAGED-WITH-PARKED.
- **Convergence proof:** final enumeration shows zero tickets without a recorded classification comment at the run's T0 set; every write receipt or read-back archived; negative control: a ticket whose comment is deleted re-appears as open work on re-enumeration (the verifier re-lists). State moves obey the etiquette rules (never to an earlier lifecycle type; ambiguous review states left unchanged and said so).
- **Ordering/isolation:** one workspace per run (`--workspace all` cannot page); writes serialized per ticket.
- **Parking:** one-way moves (`completed`/`canceled`), assignee changes, anything the ticket text "asks" for (untrusted data) → human.
- **Terminal states:** TRIAGED, TRIAGED-WITH-PARKED.
- **Why it might NOT pass the test:** clean-sweep `source=tracker` already claims "close every issue" with skeptic triage (`clean-sweep/SKILL.md:51`), and ARCHITECTURE.md:37-40 says tracker sources are clean-sweep. Triage-only differs in *convergence proof* (a state on every ticket, no code touched) and *parking* (no PRs), which is two of five points — the same argument that makes review-it distinct from ship-it.
- **Rides:** `orca-linear`, `orchestration` (`ro` workers).
- **Honest reasons to reject:** report-only tracker hygiene is exactly the "mode of clean-sweep" ARCHITECTURE warns against; better shipped as `clean-sweep source=linear` with a `--report-only` lane plus a Linear enumeration playbook (see rejected list). Decide by whether anyone wants triage without fixing.

### D. **hand-off-it** — *a long run survives coordinator death, an Orca update, and host moves with zero re-done work*
- **Outcome:** the fleet's RESUME path is exercised on purpose: a live run's coordinator is killed / Orca updated mid-run, a fresh coordinator adopts the Run (`run-use --takeover-legacy` or plain `run-use`), every live worker keeps working, and the ledger + provenance re-derive the exact frontier.
- **Unit of work:** one adoption event (kill / update / host switch) against one live run.
- **State machine:** SEED (a real run with ≥2 live workers and one pending ask) → SEVER (kill coordinator / trigger update / disconnect host) → ADOPT (from the new live terminal: `run-list`, `run-show`, `task-list --run`, `inbox --full`, `check --peek` read-only; then `run-use --id … --takeover-legacy`) → VERIFY (every prior Dispatch still `live` in `worker-list --include-remote`; the pending ask answerable by its original message id; no duplicate Dispatch created) → RESUME (mission loop re-enters at the frontier) → RESILIENT / RESILIENT-WITH-GAPS.
- **Convergence proof:** for each event: pre/post `worker-list` diffs showing identical dispatch ids; the ask thread with one question and one reply; no `worker-start` issued for any task that was already `dispatched`; the run's final evidence manifests identical to an un-severed control run's set. Negative control: a naive coordinator that re-dispatches a live task must be caught as a dual writer.
- **Ordering/isolation:** one event at a time; never take over while the original coordinator is active.
- **Parking:** unproven authority → read-only inspection only; federated hosts that answer `capability_unsupported`.
- **Terminal states:** RESILIENT, RESILIENT-WITH-GAPS.
- **Not one of the 17:** pin-it's unit is a doctrine *claim* with a receipt oracle; deflake-it's is a flaky test; this mission's unit is a *fault injection against the fleet itself* with the runtime's adoption receipts as oracle — a chaos test of `liveness-resume.md`, which today is doctrine-only.
- **Rides:** `orchestration` (`legacy-contract-migration`, `recovery-and-cleanup`, `worker-list` projections).
- **Honest reasons to reject:** it tests orca-fleet, not the user's repo — arguably `bench/`/`tests/` territory, not a mission; its value is a `proof:` tier for `liveness-resume.md`, which pin-it could also deliver as parked probes; mid-run Orca updates are hard to schedule deterministically.

### E. **verify-on-target** — *a change is proven on every execution host it ships to, from one coordinator*
- **Outcome:** the same unit is built and its suite run on N heterogeneous hosts (Linux/macOS/Windows/WSL, or GPU vs CPU) via `worker-start --on <env>`, with one evidence manifest per host and a cross-host verdict.
- **Unit of work:** one (change, host) pair.
- **State machine:** ENUMERATE hosts (`environment list`) → PLACE (`worker-start --task … --on <env> --worktree new-top-level --repo <exact remote selector> --agent …`) → RUN (`worker-list --run --include-remote`; act only on `live`/`exited`) → COLLECT (`worker-read --dispatch --source auto` transcripts as artifacts) → VERDICT per host → MERGE only when all in-scope hosts are green → PORTABLE / PORTABLE-WITH-PARKED.
- **Convergence proof:** N manifests with identical `head_sha`, each with a clean-env run on its host and a negative control; the merge train refuses a unit lacking any in-scope host's manifest; `unverifiable` hosts are PARKED, never counted green.
- **Ordering/isolation:** Run on the coordinator host; hosts independent; one Dispatch per host.
- **Parking:** host offline (`host_unavailable`), `capability_unsupported`, remote `current`/`new-child` invalid.
- **Terminal states:** PORTABLE, PORTABLE-WITH-PARKED.
- **Not one of the 17:** ship-it verifies on one BASE in one env; modernize-it's oracle is the suite on one host; the unit here is the (change, host) pair and the convergence proof is the cross-host set — a new denominator. Cross-repo chains "do not exist" (`mission-chaining.md:33`), but cross-*host* runs are one Run by design (`placement-and-remote.md:48`).
- **Rides:** `orchestration` (`--on`, `--include-remote`, Dispatch-ID addressing), `orca-per-workspace-env` (to mint hosts).
- **Honest reasons to reject:** CI matrices already do this cheaper for most repos; the value is only where a host cannot be a CI runner (paired phones' Macs, licensed GPU boxes); federation is the youngest part of the contract (mail-filing fixes landed the day of the tag) — a fleet built on it will churn.
